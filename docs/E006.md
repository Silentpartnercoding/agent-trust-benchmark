# E006 preregistration: Predicate boundary enforcement

## Frozen question

When a delegation is scoped by a **relation** ("documents belonging to org A"), does the
enforcement point verify that relation for the **specific resource requested**, or only that the
**action type** was granted?

An engine that checks only the action type will allow an out-of-scope resource while every
record still reads as in-scope. This is the cross-tenant IDOR / BOLA class. It is the gap that
after-the-fact lineage verification cannot close, because the recorded authorization and the
performed action agree — the predicate was wrong, not the record.

## Why this is a separate experiment

E001 asks whether a *forbidden action* is blocked (`payments:execute` when only
`payments:preview` was granted). That is scope enforcement on the **action** axis.

E006 holds the action constant and varies the **resource**. Both requests are
`documents:read`, both are permitted action types, and both targets are documents. Only the
relation between the resource and the delegated scope differs.

## Fixture

Two organizations, `org-a` and `org-b`, neither nested in the other.

- Human `H` holds authority over `org-a` only.
- Agent `G` has an identity distinct from `H`.
- `H` delegates to `G`: **read documents belonging to `org-a`**.
- `doc-a1` belongs to `org-a`. `doc-b1` belongs to `org-b`.
- Both documents are the same kind and both are readable by the same action.

The resource identifiers are opaque and globally unique. An engine that resolves a document by
identifier without evaluating its organization will not observe any difference between them.

## Sequence

1. Create `org-a`, `org-b`, `H`, `G`, `doc-a1`, `doc-b1`.
2. Delegate to `G`: `documents:read` scoped to `org-a`.
3. `G` reads `doc-a1` — must succeed.
4. `G` reads `doc-b1` — **must be blocked before effect**.
5. Inspect the decision input actually evaluated: did it carry the resource's organization?
6. Attempt a delegation from `H` to `G` covering `org-b`, over which `H` holds no authority —
   must be refused.
7. Revoke the `org-a` delegation; retry step 3 — must be blocked.

## Binary outputs

- `IN_SCOPE_RESOURCE_ALLOWED`
- `OUT_OF_SCOPE_RESOURCE_BLOCKED`
- `RELATION_PRESENT_IN_DECISION_INPUT`
- `RELATION_EVALUATED_NOT_ASSUMED`
- `DELEGATOR_AUTHORITY_BOUNDED`
- `SCOPE_SURVIVES_IDENTIFIER_SUBSTITUTION`
- `POST_REVOCATION_IN_SCOPE_BLOCKED`

## Numeric outputs

- `DECISION_LATENCY_MS`
- `RELATION_DEPTH_EVALUATED`
- `EVIDENCE_COMPLETENESS_PERCENT`

## The distinction this experiment exists to make

`OUT_OF_SCOPE_RESOURCE_BLOCKED` can pass for two different reasons, and they are not equivalent:

- the engine **evaluated** the resource's organization and found it outside the grant; or
- the engine **denied for an unrelated reason** — a missing role, an expired token, a default
  deny that never reached the relation at all.

`RELATION_EVALUATED_NOT_ASSUMED` separates them. It passes only where the exercised decision
surface shows the relation was an input to the decision. Where the engine returns a bare boolean
and exposes no decision input, the correct output is `INDETERMINATE` — a block that cannot be
attributed to the relation is not evidence that the relation was enforced.

`SCOPE_SURVIVES_IDENTIFIER_SUBSTITUTION` is the adversarial form: the same request with only the
resource identifier changed. An engine that passes `OUT_OF_SCOPE_RESOURCE_BLOCKED` but fails this
is enforcing something other than the relation.

## Status vocabulary

As E001. `PASS`, `FAIL`, `BLOCKED_EXTERNAL_ACCESS`, `NOT_SUPPORTED`, `INDETERMINATE`.
Absence is never inferred from an unsearched surface. An engine may be reported `NOT_SUPPORTED`
for a relation-scoped grant only where the exercised interface makes that boundary explicit;
otherwise `INDETERMINATE`.

## Fairness rules

- Every engine receives the same semantic fixture and the same output schema.
- The policy expressing "documents in org-a" is written in each engine's native form. It is not
  translated from a single source, because the question is whether the engine's own model can
  express and enforce the relation.
- Each policy is recorded verbatim in the result. A weaker policy is a finding about the
  engine's expressiveness, not a benchmark error to be corrected silently.
- Benchmark-generated observations are labelled as such; they are not called engine-native
  decisions.

## Out of scope

Whether the delegation was recorded verifiably, and whether it can be re-derived offline. That is
the lineage question addressed by attestation formats. E006 asks only whether the runtime
enforced the boundary the predicate implies.

## Amendment 1 — the relation input the caller supplies

**Written before the fixture exists and before any result from it. Prompted by
@Santoshkumarpuppala on OWASP www-project-mcp-top-10#44, offered there as a hypothesis from a
labelled set of web-application authorization findings rather than as a measurement.**

### The gap

E006 fixes `grant_org` in `BASE` and varies `resource_org` across its three decision inputs. The
axis it varies is the resource's organization. It never varies the organization the grant
asserts.

The `relation-aware` policy decides on `input.resource_org == input.grant_org`. Both sides are
inputs to the decision. Nothing in the experiment establishes where `grant_org` came from, and
the reported failure shape is that in deployed systems it is frequently taken from the request
body rather than from the session or the grant record.

Where that holds, the relation is present in the decision input, it is genuinely evaluated, and
it is computed over a value the caller chose. The identifier-substitution check varies the
resource identifier, not the organization, so it does not reach the case either.

### What will be exercised

A third policy, `caller-controlled-relation`, identical to `relation-aware` except that the
organization it compares against is read from a caller-supplied field rather than from the grant.
A fourth decision input supplies a resource in `org-b` together with a caller-asserted
organization of `org-b`, while the grant names `org-a`.

### Predicted outcomes, recorded in advance

1. **The caller-controlled policy passes all five existing checks.** In-scope allowed, out-of-scope
   blocked, relation present, relation evaluated, and scope surviving identifier substitution.
2. **It permits the cross-organization read** when the caller supplies a matching organization,
   which is a tenant boundary crossed with every current check green.
3. **A new check, `RELATION_INPUT_NOT_CALLER_CONTROLLED`, fails on it and passes on
   `relation-aware`.** The check compares the decision reached under the grant's organization
   with the decision reached when only the caller-asserted organization differs. If the outcome
   changes, the relation input is caller-controlled.
4. **`action-only` and `relation-aware` results are otherwise unchanged** by the addition. If any
   existing check moves, the new fixture has altered the experiment rather than extended it.

Predictions 1 and 3 are the falsifiable ones. If prediction 1 fails — if an existing check
already catches this — then the gap does not exist and the amendment should be withdrawn rather
than kept.

### What this amendment does not cover

Two further shapes were reported in the same comment and are **not** addressed here, so that
their absence is recorded rather than implied to be covered:

- The relation enforced on one verb of an endpoint family and not another.
- The relation enforced at a router or middleware layer, with a second route reaching the same
  handler without passing through it.

Both are properties of how a policy is wired into an application rather than of the policy's own
decision surface, which is what E006 exercises. They would need a different experiment.

### Provenance of the hypothesis

The shapes come from a labelled corpus of web-application authorization findings, not from MCP
deployments, and the contributor stated plainly that they had not measured whether the shapes
transfer. This amendment tests whether the shape is expressible and detectable at the decision
surface. It does not establish how often it occurs in MCP deployments, and no result from it
should be read as though it did.

## Amendment 2 — is the delegation bound to the agent presenting it?

**Written before the fixture exists and before any run of it.**

### Prior probe, disclosed

Amendment 1 came from an external hypothesis. This one came from applying the same method to the
rest of the decision surface, and it began with an exploratory probe rather than a prediction.

Enumerating which fields the experiment ever varies showed that four never change across any
decision input: `token_active`, `roles`, `agent_id` and `delegation_id`. Probing each against
`relation-aware` showed that an inactive token, an empty role set and an ungranted role are all
correctly denied, and that **a different `agent_id` presenting the same `delegation_id` is
permitted**, as is a different `delegation_id`.

That probe is disclosed here because it preceded the predictions below and therefore cannot be
counted as confirming them. What follows is what a fixture built to test it is expected to show.

### The gap

E006's policies check `input.agent_id != ""` and `input.delegation_id != ""`. Neither establishes
that the agent presenting the delegation is the agent the delegation was issued to. Both fields
are present in the decision input and both are evaluated, so `RELATION_PRESENT_IN_DECISION_INPUT`
and `RELATION_EVALUATED_NOT_ASSUMED` are satisfied by a policy that binds neither.

This is the same shape as Amendment 1 one axis over: a field that sits in the decision, is never
varied by the experiment, and turns out never to have been bound.

It matters more here than it would in a production review, because `relation-aware` is the
reference policy this experiment holds up as correct. A suite that certifies it while it accepts
any agent is certifying the wrong thing.

### What will be exercised

`BASE` gains `delegation_agent`, recording the agent the delegation was issued to. A fifth
decision input, `AGENT_SUBSTITUTED`, is the in-scope request with only `agent_id` changed to an
agent the delegation does not name. A fourth policy, `agent-bound`, is `relation-aware` plus a
requirement that the presenting agent equal the delegation's agent.

### Predicted outcomes, recorded in advance

1. **`relation-aware` permits the substituted agent** and therefore fails a check that observes
   it, while passing all six existing checks unchanged.
2. **`action-only` and `caller-controlled-relation` also fail it**, neither having any agent
   binding either.
3. **`agent-bound` passes all seven**, including Amendment 1's check, since it inherits
   `relation-aware`'s grant-sourced organization comparison.
4. **No existing check moves on any policy.** If one does, the fixture has altered the experiment
   rather than extended it.

Predictions 3 and 4 are the falsifiable ones. Prediction 1 was probed before this was written and
is reported as confirmation of the probe, not as an independent result.

### What this does not establish

That agent substitution occurs in deployed MCP systems. This shows the property is expressible
and detectable at the decision surface and that the experiment's own reference policy lacked it.
Frequency is not measured here and no result from this should be read as though it were.

## Amendment 3 — what the suite can actually detect the absence of

**Written before the harness exists and before any run of it.**

### Why a third amendment rather than a third check

Amendments 1 and 2 fixed two instances of one pattern: a field present in the decision input,
never varied by the experiment, and never actually bound by the policy. Both were found by a
person noticing. Adding a check per instance means waiting for the next person.

The generalisation is not "every field must vary." That over-flags: `grant_org` and
`delegation_agent` never vary across any input, yet both are covered, because the adversarial
inputs vary what they are compared *against*. Field-level variation is the wrong unit.

The right unit is the condition. For each condition in the reference policy, if that condition
were simply deleted, would any check in this suite fail? If not, the suite cannot claim the
property is enforced — it would certify a policy that omits it.

That is mutation coverage, and it is mechanically computable from the fixtures without anyone
reviewing anything.

### What will be exercised

`agent-bound` is the reference policy after Amendment 2. For each condition in its `allow` rule,
a variant is generated with that single condition removed, and the full check suite is run
against the variant. A condition is **covered** if at least one check moves to FAIL, and
**undetected** if every check still passes.

The output is a coverage table over the reference policy's own conditions. No new check is added
to the suite by this amendment.

### Predicted outcomes, recorded in advance

1. **Undetected: `input.token_active == true`.** Every decision input sends `true`, so a policy
   omitting the condition behaves identically on all of them.
2. **Undetected: `"documents_read" in input.roles`** and **`input.action == "documents:read"`**,
   for the same reason. The action axis is E001's and is deliberately fixed here, so this one is
   expected and is not a defect; it is recorded so the boundary is visible rather than assumed.
3. **Undetected: `input.agent_id != ""` and `input.delegation_id != ""`.** Both are non-emptiness
   tests over values no input ever empties.
4. **Covered: `input.resource_org == input.grant_org`**, by `OUT_OF_SCOPE_RESOURCE_BLOCKED`,
   `SCOPE_SURVIVES_IDENTIFIER_SUBSTITUTION` and `RELATION_INPUT_NOT_CALLER_CONTROLLED`.
5. **Covered: `input.agent_id == input.delegation_agent`**, by `DELEGATION_BOUND_TO_AGENT`.
6. **Covered: `input.resource_org != ""`** is expected to be undetected, since no input supplies
   an empty organization.

Predictions 4 and 5 are the falsifiable ones that matter: if a condition the suite was built to
enforce turns out to be undetected, the corresponding check does not do what it claims.

### What this does not do

It does not add checks, and it does not make the undetected conditions safe. It reports which
properties this suite is entitled to claim it verifies. Closing the gaps it reports would require
further adversarial inputs, and each would need its own amendment.

It also cannot find a property absent from the reference policy altogether. Mutation coverage
measures what the suite detects the removal of; a condition nobody wrote is invisible to it. Both
earlier amendments were exactly that case, and neither would have been caught by this.
