# E007 preregistration: Enforcement-path coverage

## Status

**Preregistered before the fixture exists and before any run.**

The fixture and predictions below were prompted by a review exchange on
OWASP `www-project-mcp-top-10` issue #44. The reported failure shapes came
from labelled web-application authorization findings, not measured MCP
deployments. E007 tests whether those shapes are expressible and detectable;
it does not establish their prevalence in MCP systems.

## Frozen question

Can an authorization policy be correct whenever it is evaluated, while an
application still permits an out-of-scope action because one verb or route
reaches the protected object without traversing the enforcement guard?

E006 tests the **decision surface**: whether the policy evaluates the right
relation over trustworthy inputs. E007 tests the **reachability surface**:
whether every application path to the object actually invokes that policy.

## Why this is a separate experiment

E006 cannot observe an authorization decision that never occurs. A correct
policy can deny every adversarial input supplied to it and still protect
nothing on a route that bypasses the policy entirely.

Changing E006 to include HTTP routing would alter its frozen question and make
its earlier results incomparable. E007 therefore reuses the relation boundary
but varies the wiring between routes, handlers, guards, and effects.

## Fixed semantic fixture

- Two organizations, `org-a` and `org-b`, neither nested in the other.
- Agent `G` has `documents:read` and `documents:write` authority scoped to
  `org-a`.
- One protected object, `doc-b1`, belongs to `org-b`.
- The authorization policy is identical in every arrangement: allow only when
  the requested action is granted **and** `resource_org == grant_org`.
- An entitled control uses the same actions and object with a grant scoped to
  `org-b`.

The out-of-scope and entitled requests differ only in the trusted grant
organization. Route, verb, object identifier, handler, and policy source stay
fixed.

## Fixed reachability surface

The object is reachable through three entry points:

1. `GET /documents/doc-b1` reaches the read handler.
2. `POST /documents/doc-b1` reaches a separate write handler.
3. `GET /legacy/documents/doc-b1` reaches the same read handler as entry 1.

The canonical routes and late alias MUST be registered in different modules.
The alias MUST be registered after guard configuration, so the fixture does
not place both route declarations next to each other and make the bypass
artificially obvious.

## Guard-placement matrix

The guard placement is recorded as data, not inferred from a denial.

### Complete controls

Each complete arrangement must protect all three paths:

- `router-complete`: all routes belong to the guarded router.
- `middleware-complete`: application-wide middleware covers all routes.
- `decorator-complete`: both handlers are wrapped by the guard.
- `handler-complete`: both handlers invoke the guard before effect.

### Intentionally incomplete arrangements

- `verb-asymmetric`: the write handler is guarded and the read handler is not.
  Both GET routes reach the unguarded read handler.
- `router-late-bypass`: canonical routes belong to the guarded router; the
  later alias is registered directly on the application outside it.
- `middleware-late-bypass`: middleware covers the canonical route prefix; the
  later alias is registered outside that scope.

These are wiring controls, not claims that routers, middleware, or decorators
are inherently unsafe.

## Sequence

For every arrangement:

1. Evaluate the out-of-scope request directly against the policy and record
   the denial.
2. Snapshot the effect ledger and guard-invocation ledger.
3. Send out-of-scope read, write, and late-alias requests.
4. Record status, handler reached, whether the guard ran, decision, and effect
   delta for each request.
5. Send the three corresponding entitled-control requests.
6. Record the complete route inventory, registration source, registration
   order, handler identity, and guard scope.
7. Compare all persistent fixture state with the pre-run snapshot.

No raw credential or secret is required or retained. The fixture uses explicit
test identities and a deterministic in-memory policy.

## Binary outputs

- `POLICY_DENIES_OUT_OF_SCOPE_WHEN_CALLED`
- `OUT_OF_SCOPE_READ_BLOCKED_BEFORE_EFFECT`
- `OUT_OF_SCOPE_WRITE_BLOCKED_BEFORE_EFFECT`
- `OUT_OF_SCOPE_ALIAS_BLOCKED_BEFORE_EFFECT`
- `GUARD_INVOKED_ON_EVERY_OUT_OF_SCOPE_PATH`
- `ZERO_UNAUTHORIZED_EFFECTS`
- `ENTITLED_READ_ALLOWED`
- `ENTITLED_WRITE_ALLOWED`
- `ENTITLED_ALIAS_ALLOWED`
- `ROUTE_INVENTORY_COMPLETE`
- `LATE_REGISTRATION_COVERED`

## Recorded evidence

- Policy source digest and direct policy decision.
- Route, method, handler, registration module, and registration order.
- Declared guard placement and guard scope.
- Per-request guard invocation and decision.
- Before/after effect ledger with an explicit expected delta.
- HTTP-equivalent status and bounded diagnostic.

## Predicted outcomes, recorded in advance

1. **The direct policy check denies the out-of-scope request in all seven
   arrangements.** If it does not, the fixture contains a policy defect and
   cannot test enforcement-path coverage.
2. **All four complete controls pass every output.** This is the principal
   falsifiable control: if any complete arrangement misses a path, the fixture
   does not implement that placement faithfully.
3. **`verb-asymmetric` permits both out-of-scope GET requests and blocks the
   out-of-scope POST.** The guard-invocation ledger contains no entry for the
   two read paths, and the effect ledger records two unauthorized reads.
4. **`router-late-bypass` blocks both canonical paths and permits only the
   late alias.** The alias reaches the same read handler but has no guard
   invocation.
5. **`middleware-late-bypass` has the same externally observable outcome as
   prediction 4, while the recorded guard placement distinguishes the cause.**
6. **Every entitled-control request succeeds in every arrangement.** A fixture
   that only denies cannot demonstrate authorization enforcement and is not a
   valid positive control.
7. **Every unauthorized success has a matching effect, and every denial has
   zero effect.** A status-only result is insufficient evidence of pre-effect
   enforcement.
8. **The late alias has a greater registration order and a different
   registration module from the canonical routes.** If not, the fixture does
   not reproduce the review-resistant shape it claims to model.

Predictions 2, 3, 4, and 5 are the discriminating predictions. They must not be
rewritten after implementation to match observed behavior.

## Success and failure rules

The experiment succeeds as an instrument only if:

- every complete control passes;
- each intentionally incomplete arrangement fails exactly the predicted path
  coverage checks;
- the direct policy result remains a denial throughout;
- guard and effect ledgers agree with every reported outcome; and
- the entitled controls prove the application is not merely default-denying.

An unexpected result is retained as a failed prediction. It is not corrected
silently by changing the fixture or oracle.

## Boundaries

- This is a synthetic application-routing fixture, not a measured MCP product
  or production framework.
- It establishes that the failure shapes are expressible and detectable, not
  how often they occur.
- It does not test framework-specific route discovery, generated routes,
  reverse proxies, service meshes, or calls that bypass the application
  process entirely.
- It does not measure its own false-positive rate against a real labelled
  corpus. The entitled controls prevent default-deny false confidence but do
  not substitute for independently labelled benign cases.
- The policy and object store are deliberately small. E006 remains the evidence
  for predicate-input and agent-binding failures.
