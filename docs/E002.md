# E002 preregistration: witnessed human authorization receipt

## Frozen question

Can a provider-neutral receipt close E001's human-attribution gap by binding a
witnessed human authorization event to the exact agent identity, key, audience,
scope, action credential, and revocation state used at enforcement time?

## Hypotheses

1. A trusted issuer's interactive-authorization receipt plus a credential bound
   to its digest makes human attribution directly verifiable at the gate.
2. Changing the receipt, agent identity, agent key, audience, scope, action, or
   validity interval causes a pre-effect rejection.
3. An administrator-configured link cannot satisfy a policy requiring
   interactive authorization merely by labelling itself as human delegation.
4. Revoking the receipt causes the next checked action to be rejected; an
   unavailable revocation answer produces `INDETERMINATE`, never an allow.

## Fixed sequence

1. A human authenticates and interactively authorizes `payments:preview` for one
   distinct agent key and the payments audience.
2. The trusted issuer creates a signed receipt with a five-minute lifetime and
   a receipt-specific revocation handle.
3. The issuer creates an agent action credential cryptographically bound to the
   digest of that exact signed receipt.
4. The gate verifies both and allows `payments:preview` exactly once for the
   exercised effect.
5. The gate rejects `payments:execute` before effect.
6. Repeat with one mutation at a time: receipt swap, agent swap, key swap,
   audience swap, scope expansion, expired receipt, untrusted proof format, and
   administrator-configured authorization.
7. Revoke the receipt, retry `payments:preview`, and measure from acknowledged
   revocation to the first proven pre-effect block.
8. Reconstruct the human event, receipt, credential binding, gate decision, and
   effect count without retaining raw secrets or bearer credentials.

## Binary outputs

- `TRUSTED_ISSUER_PROVEN`
- `HUMAN_AUTHORIZATION_WITNESSED`
- `AGENT_IDENTITY_BOUND`
- `AGENT_KEY_BOUND`
- `CREDENTIAL_RECEIPT_BOUND`
- `AUDIENCE_BOUND`
- `ALLOWED_ACTION_SUCCEEDS`
- `FORBIDDEN_ACTION_BLOCKED`
- `RECEIPT_SWAP_BLOCKED`
- `UNAVAILABLE_REVOCATION_FAILS_CLOSED`
- `ADMIN_LABEL_REJECTED_AS_CONSENT`
- `REVOCATION_SUPPORTED`
- `POST_REVOCATION_ACTION_BLOCKED`
- `FULL_PATH_AUDITABLE`

## Numeric outputs

- `REVOCATION_LATENCY_MS`
- `RECEIPT_LIFETIME_SECONDS`
- `VERIFICATION_LATENCY_MS`
- `EVIDENCE_COMPLETENESS_PERCENT`

## Fixed verdict rule

Only `VERIFIED` permits the effect. `REJECTED` and `INDETERMINATE` both block
the action. `INDETERMINATE` remains visible in the report so missing evidence is
not misreported as proof of an attack or proof of safety.

## First live adapters

Run the same receipt contract through Keycloak and ZITADEL while keeping OPA and
the resource action fixed. The purpose is not to make either provider look
complete. It is to measure where each can natively witness the human event,
issue or bind the receipt, expose revocation, and preserve audit evidence.

No provider surface is included until its API and intended authorization
contract are available for review.
