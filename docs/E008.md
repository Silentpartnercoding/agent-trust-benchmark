# E008: actor binding in an offline authorization-lineage verifier

Status: exploratory. **Not preregistered**, and that matters for how much weight this carries.
E006 and E007 fixed their questions and predictions before anything was built. E008 did not. The
arms below were run while checking a claim made by a third party in a public thread, and the
write-up followed. The expectations now recorded in `experiments/e008/probe.mjs` were fixed before
the result file was generated, so a later change in the subject surfaces as `DIVERGED` rather than
being quietly absorbed, but they cannot be counted as predictions made in advance of first
observation. This follows the same disclosure the E001 re-runs carry, and the "prior probe,
disclosed" note in E006 Amendment 2.

The question is narrow. When an authorization record binds an action to the agent a grant names,
rather than leaving that binding to each deployment's policy, does the binding hold, and does it
hold everywhere it needs to?

That question comes out of E006. Its `DELEGATION_BOUND_TO_AGENT` check found that three of the four
policies tested treat a delegation as a bearer credential: any agent presenting the identifier
inherits the authority, while every relation check still reads green, because the agent identifier
sits in the decision input and is evaluated but never compared to the delegation. `relation-aware`,
the policy that experiment held up as correct, fails it too. The natural follow-on is whether moving
the binding into the record format fixes the class, and the VAL protocol is a public implementation
that claims to do exactly that.

The subject is `@val-protocol/chain-verifier` 0.11.2, installed from npm and pinned in
`experiments/e008/package.json`. Six chains are generated, each differing only in how the grant
names its actor and which agent performs the action. The grant names `agent:legit`; in five of six
arms the action is performed by `agent:impostor`. Nothing is hand-written: the runner constructs
every chain, calls the published verifier, compares each verdict against the expectation held in the
same file, and emits `results/e008/e008-val-actor-binding-v1/result.json`.

What the six arms found, with all six matching expectation:

| Arm | Grant names | Acted as | `scope` | `authority` |
|---|---|---|---|---|
| Root grant sets the subject clause | `agent:legit` | impostor | **red** | green |
| Control: the named agent acts | `agent:legit` | legit | green | green |
| Root grant omits the subject clause | nothing | impostor | **green** | green |
| No subject clause, `v: 3` body carrying `grantee` | `agent:legit` | impostor | green | **red** |
| Sub-assignment drops the clause its root set | `agent:legit` | impostor | **red** | green |
| Sub-assignment names the impostor instead | impostor | impostor | **red** | green |

Two conclusions, and they should not be run together.

Where the grant names its actor, the binding holds, and it holds more strongly than E006 tested for.
The last two arms are the ones built to break it. Scope in this protocol is the intersection of a
grant with every ancestor back to the root, so a sub-delegation can neither drop the subject clause
nor widen it to somebody else. No delegation chain escapes the binding its root established, and no
arrangement was found that did. That is a genuine answer to the E006 finding, and it is a property
of the format rather than of any deployment's policy.

The third arm is the exception, and it is a default rather than a defect in the mechanism. The
subject clause is optional. Where a root grant omits it, integrity, lineage, scope and authority all
verify green for an action performed by an agent the grant never named, and because effective scope
intersects back to the root, no descendant can repair it. The specification is not self-consistent
here: §6.6 states the principal match as an unconditional conjunct of satisfaction and carries no
"where present" qualifier, unlike the validity-window conjunct three lines below it, while §6.2
declares every top-level key optional and annotates the subject clause as required only for
non-root assignments. The verifier resolves that in favour of optionality. Under a literal reading
of §6.6, the third arm should be red.

The fourth arm records a second, separate mechanism. A `grantee` field on an assignment body at
version 3 produces an authority failure through a check the implementation calls agent-equity. It is
absent from the specification entirely, documented only in the verifier package's changelog at
0.5.0, and it does not engage on the body versions the specification defines.

Boundaries. This is a synthetic six-arm fixture against one implementation at one version, not a
survey and not a deployment. It establishes that the binding is expressible in a record format and
that sub-delegation cannot escape it. It says nothing about how often deployments set the optional
clause, and nothing about implementations other than this one.

One thing the arms cannot reach, worth stating because it survives every result above. The wire
format carries no per-block signature; §4.3 says so and §7.5 repeats it. The acting principal is a
string the operator's own emitter writes into the canonical block content. So the comparison, in
both mechanisms, is between two operator-authored strings inside one operator-authored record. The
hash chain makes them tamper-evident after emission; neither is authenticated at emission. An
emitter that records the authenticated actor and one that copies the name out of the grant it just
resolved produce byte-identical exports. Which behaviour produced a given chain has no
representation in the bytes, so the binding relocates the bearer-credential assumption from the
policy engine to the emitter rather than removing it. That is a real improvement, because an emitter
is a far smaller and more auditable surface than a policy engine, and it is not elimination.

To reproduce: `cd experiments/e008 && npm ci && node probe.mjs`. The runner rewrites the result file
and exits non-zero if any arm diverges from its recorded expectation.
